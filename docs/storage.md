# Storage profile and disk safety

Run `pnpm retention --profile` for measured SQLite `dbstat` bytes by table and index, row counts, recent rows, and estimated daily bytes by table. This query scans the database and should run outside peak ingestion. Data health shows the database file, WAL, free disk, and estimated runway. Sprint 8 thresholds are WARNING below 30 GiB, HIGH below 20, CRITICAL below 10, and EMERGENCY below 5. See [storage-emergency.md](storage-emergency.md).

Data health also estimates post-version row growth, but readiness V2 uses measured positive table/index allocation over at least four hours, with a limit of 0.15 GiB/day and runway of 180 days. Timestamp estimates can miss delayed ingestion of old events. The first measured Sprint 8 run allocated 0.7908 GiB/day and failed both storage gates; see [sprint8-validation.md](sprint8-validation.md).

On 2026-09-28 before Sprint 7 migration, the 8.35 GiB database had roughly 7.11 GiB in `pool_snapshots`, about 226 MiB in `fee_events`, and about 149 MiB in `price_observations`. Full snapshots were adding roughly 341,000 rows and 1.1 GiB per day. The primary mitigation is reducing new full JSON writes while retaining independent compact one-minute observations. Price observations with no source timestamp, or an identical source/timestamp/price already stored, are not appended. Historical source timestamps and provenance are never rewritten into artificial buckets.

The `pool_snapshots` primary-key index and `snapshots_pool_time` each occupied about 150 MiB. Sprint 8 migration 0011 removes the latter after query-plan proof that the primary-key index serves the same pool/time queries. The separate time index remains. WAL stays enabled; freed pages are reused. `VACUUM` is manual and needs enough temporary free space. Do not run it during ingestion or while disk is scarce. No old rows were rewritten or deleted by this migration.
